WebXR: rendering via an intermediate framebuffer distorts stereo on visionOS

Two buttons below run the same scene with the same matrices and the same per-eye viewports. The only difference is where the frame is drawn:

  • A — direct: draws into XRWebGLLayer.framebuffer. Correct.
  • B — intermediate: draws into a texture-backed framebuffer of identical size, then copies it to XRWebGLLayer.framebuffer with a fullscreen triangle. Distorted. (You might need to look up to find the cubes.)

Expected

Both render identically: a row of seven cubes plus one nearer cube, in correct stereo. They sit at 1.6m, so depending on the reference space granted you may need to look up.

Actual, on visionOS

B is badly distorted — legible near the centre of view and degrading rapidly toward the edges, with objects appearing in only one eye depending on their position. A is correct.

Notes

  • No library. Hand-written GLSL, raw WebGL2, raw WebXR.
  • Both framebuffers are the same size and report FRAMEBUFFER_COMPLETE.
  • Not format-dependent: reproduces with RGBA8 and with RGBA16F.
  • Correct on Android Chrome (Samsung Galaxy XR) for both A and B.
  • An intermediate-plus-copy is what three.js does whenever the output needs a colour transform, which is how this was found — but three.js is not required to reproduce it.
