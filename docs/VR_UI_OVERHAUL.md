# VR UI Overhaul: Radius, Sliders & Performance (v0.6.153)

## Overview
This document details the refactoring and debugging of the VR User Interface in SculptXR, specifically targeting the functional breakdown of sliders ('Radius', 'Intensity') and the disconnection between tool state and VR visual feedback.

## Key Issues Resolved

### 1. The "Stale Slider" Bug
*   **Symptoms**: Sliders were non-responsive or reset instantly.
*   **Root Cause**: The VR Menu (`GuiXR.js`) was generating widgets once at startup and caching them indefinitely. `activeTool` references in `GuiVRTools.js` were captured at init time (pointing to the default tool) and never updated when the user switched tools.
*   **Fix**: 
    1.  Updated `GuiXR.js` -> `refreshToolsWidget()` to clear `this._tabWidgets` cache.
    2.  Updated `GuiVRTools.js` to accept `activeToolIndex` or fetch it dynamically if undefined.

### 2. The "Legacy Scaling" Bug
*   **Symptoms**: Radius slider would jump to insane values (e.g., 5000) or lock up.
*   **Root Cause**: Radius and Intensity sliders lacked an `onInput` handler. `GuiXR.js` has a specific optimization/fallback for sliders *without* `onInput` where it calls `updateRadius()`. This legacy method multiplied the value by 100 (!), assuming a normalized 0-1 input, whereas the widgets were defined with explicit ranges (5-250).
*   **Fix**: Added explicit `onInput` handlers to `GuiVRTools.js` for Radius/Intensity, matching the pattern used by the working 'Curvature' slider in `GuiVRRendering.js`.

### 3. The "Detached Cursor" Bug
*   **Symptoms**: Sliders updated the tool's internal numbers, but the red/blue cursor ring in VR remained static/default size.
*   **Root Cause**: `Scene.js` (rendering loop) was calculating the `pickingRadius` based on `GuiXR._radius` (the menu's internal state) rather than the active tool's actual `_radius`. The menu state and tool state were de-synced.
*   **Fix**: Updated `Scene.js` to prioritize `sculptManager.getCurrentTool()._radius` (normalized / 100.0) if available.

### 4. Syntax & Deploy Blockers
*   **Incident**: A malformed `} else if` caused a syntax error in production.
*   **Resolution**: Fixed immediately (v0.6.149) and verified.

## Architecture Notes

### Widget Generation
*   Widgets are generated by modules in `src/gui/vr/` (e.g., `GuiVRTools.js`).
*   They are **NOT** reactive by default. You **MUST** clear the cache (`this._tabWidgets = {}`) in `GuiXR.js` if the underlying data structure (like which tool is active) changes.

### Event Handling
*   `GuiXR.js` handles raw pointer events (`_handleWidgetClick`, `_handleWidgetDrag`).
*   **Best Practice**: Always provide an `onInput(val)` callback for sliders. Relying on generic automatic binding is fragile and prone to legacy scaling assumptions.

### Default Layout (v0.6.153)
*   **Rendering**: Collapsed
*   **Topology**: Collapsed
*   **Sculpting & Painting**: Expanded
*   Managed via `this._sectionStates` in `GuiXR` constructor.

## Future Recommendations
*   **Unified State**: The UI currently duplicates state (GuiXR vs SculptManager). Moving to a single source of truth (Signal/Observer pattern) would prevent de-syncs.
*   **Reactive UI**: The manual cache clearing is a band-aid. A lightweight reactive view system (retrained mode?) would be safer.
